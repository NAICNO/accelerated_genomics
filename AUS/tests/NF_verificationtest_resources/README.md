# NF Verification Test - Resource Sweep Regression Gate

## Purpose

`nf_resource_sweep_verification.nf` is a regression-gate verification test for Nextflow cluster-identity and resource-sizing profile configuration. It verifies that every process currently defined under `AUS/modules/*.nf` resolves to the expected resource settings when a cluster identity profile is combined with a resource-sizing profile.

This is not a functional genomics test and it does not execute Parabricks, GATK, containers, or real analysis inputs. The workflow uses lightweight stub processes that only `echo` the resolved task metadata from inside each process context.

The gate is intended to catch configuration regressions such as:

- changed `withName` selector behavior
- changed `withLabel` selector behavior
- broken profile composition between cluster and resource configs
- unintended changes to CPU, time, or memory sizing for real workflow processes
- drift between the verification workflow's stub process list and the actual module process inventory

## Regression-gate claim

The gate passes only when all of the following are true:

- the stub inventory in `nf_resource_sweep_verification.nf` still matches the real process names and labels in `AUS/modules/*.nf`
- each cluster/resource profile combination runs to completion
- each run writes a TSV with one row per covered process plus the header row
- the generated TSV for each combination matches the checked-in golden reference for that combination, or matches an explicitly approved new baseline during a controlled update

If any of those conditions fail, the shared config layer should not be treated as release-ready.

## Files in this test

- `nf_resource_sweep_verification.nf`: stub workflow that emits one row per process with the resolved `task.cpus`, `task.time`, `task.ext.mem_gb`, and label.
- `nf_resource_sweep_verification.config`: test-specific config that reuses the real cluster and resource config files.
- `check_stub_sync.sh`: inventory guard that compares the stub workflow's process coverage against `AUS/modules/*.nf` before trusting a sweep run.
- `golden/`: checked-in expected TSVs, one per cluster/profile combination.
- `results/`: optional local archive area for dated or ad hoc sweep outputs.

## What the workflow validates

- The workflow covers the current real module process inventory (i.e., processes in `AUS/modules`)
- For each stub process, the TSV row is generated by interpolating values directly from that process's own task context
  - `workflow.profile`
  - `task.cpus`
  - `task.time`
  - `task.ext.mem_gb`
  - the process label encoded by the stub

This gives evidence about the actual merged config state seen by the process, not about a copied table of expected values.

## Config under test

The verification config composes the same shared config files the pipelines use:

- cluster identity profiles:
  - `AUS/configs/PARABRICKS_TSD.conf`
  - `AUS/configs/PARABRICKS_FOX.conf`
- resource-sizing profiles:
  - `AUS/configs/resources_production.conf`
  - `AUS/configs/resources_test.conf`

The test deliberately does not include the `singularity` profile. The stub processes have no `container` directive and only execute `echo`, so container-engine validation is out of scope for this gate.

The workflow also mirrors the real fail-fast behavior used by the workflow entrypoints: it aborts immediately if neither `production` nor `test` is included in `-profile`.

## Output contract

Each successful run writes `resource_sweep_results.tsv` in the current directory and overwrites any existing file of the same name.

The TSV schema is:

```text
cluster_profile	process	cpus	time	mem_gb	label
```

Each successful run should produce `resource_sweep_results.tsv` with:

- One header row
- One row for each covered process (i.e, `N` data rows; `N` == # of processes)
- Rows sorted lexicographically (`collectFile(..., sort: true)`)

The run also writes a trace file:

```text
trace_nf_resource_sweep_verification.txt
```

## Preconditions

1. Run commands from `AUS/tests/NF_verificationtest_resources` so relative config paths and output paths match this specification.
2. Tested with Nextflow `>=26.08.0-edge`
3. For TSD, replace the placeholder project value in `AUS/configs/PARABRICKS_TSD.conf` if that has not already been done.
4. For Fox, confirm `params.account` in `AUS/configs/PARABRICKS_FOX.conf` matches the target project.
5. Run the stub drift check before trusting any sweep output.

## Test procedure

### Step 1: verify stub coverage is in sync

Run:

```bash
./check_stub_sync.sh
```

Pass condition:

```text
OK: stub process list and labels match modules/*.nf (`<N>` processes).
```

Fail condition:

- any process defined in `AUS/modules/*.nf` is missing from the stub workflow
- any stubbed process no longer exists in `AUS/modules/*.nf`
- any real process label differs from the label encoded in the stub workflow

If this step fails, stop. Update the stub workflow and the drift-check expectation list before using this test as a gate.

### Step 2: run the four profile combinations

```bash
nextflow run nf_resource_sweep_verification.nf -c nf_resource_sweep_verification.config \
  -profile <profile combination>
```

- Run 1: TSD + production sizing (`-profile tsd,production`)
- Run 2: TSD + test sizing (`-profile tsd,test`)
- Run 3: Fox + production sizing (`-profile fox,production`)
- Run 4: Fox + test sizing (`-profile fox, test`)
- **NOTE:** Tag `resource_sweep_results.tsv` with date and move to results directory
  - (`mv resource_sweep_results.tsv results/fox_test_$(date +%Y%m%d).tsv`)

### Step 3: compare each run to its golden TSV

Example comparisons:

```bash
diff -u golden/tsd_production.tsv results/tsd_production_$(date +%Y%m%d).tsv
diff -u golden/tsd_test.tsv results/tsd_test_$(date +%Y%m%d).tsv
diff -u golden/fox_production.tsv results/fox_production_$(date +%Y%m%d).tsv
diff -u golden/fox_test.tsv results/fox_test_$(date +%Y%m%d).tsv
```

Pass condition:

- all four diffs are empty

Fail condition:

- any changed row in CPU, time, memory, label, or profile string
- missing rows
- added rows
- changed header schema

Any diff must be treated as a config regression until it is explained and explicitly accepted.

## Optional negative test

Confirm the workflow fails fast when no resource-sizing profile is selected:

```bash
nextflow run nf_resource_sweep_verification.nf -c nf_resource_sweep_verification.config \
  -profile tsd
```

Expected message:

```text
No resource-sizing profile selected. Add `production` or `test` to -profile alongside `tsd`/`fox`, e.g. -profile tsd,test
```

No sweep TSV should be treated as valid from this run.

## Acceptance criteria

Treat the release gate as passing only if all criteria below are satisfied:

- `check_stub_sync.sh` passes
- all four profile combinations complete successfully
- each run emits a TSV with the expected schema and row count
- each generated TSV matches its corresponding file under `golden/`

If the sweep output differs from the golden reference and there is no approved explanation, block the release.
